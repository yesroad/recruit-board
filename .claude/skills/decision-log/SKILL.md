# Decision Log Skill

설계 판단을 루트 `DECISIONS.md` 에 기록한다.
기능 단위가 아니라 **판단이 갈린 순간** 에 호출한다 — 후보가 둘 이상이었을 때, AI 제안을 기각했을 때,
요구사항이 모호해 가정을 세웠을 때, 기능을 포기하거나 미뤘을 때.

## 기록 항목

주요 결정 3~5개를 아래 형식으로 남긴다. 대상은 상태 관리 방식, 낙관적 업데이트 롤백 전략,
폴더 구조, 라이브러리 선택 등이다.

```markdown
## <결정 제목>

- 결정. <무엇을 택했나>
- 후보. <검토한 다른 선택지>
- 근거. <왜 이것인가>
- 버린 이유. <다른 것을 왜 버렸나>
```

이와 별도로 아래 세 절을 유지한다. 비어 있으면 채우도록 사용자에게 묻는다.

1. **AI 제안 중 기각한 것** — 무엇을 제안받았고 왜 쓰지 않았는지. 빼먹기 쉬우니 매번 확인한다.
2. **못 끝낸 기능** — 무엇을, 왜 남겼는지. 이유가 명확하면 미완성 자체는 문제가 되지 않는다.
3. **세운 가정** — 요구사항이 모호했던 지점과 어떻게 해석했는지.

## 문장 규칙 — 커밋 메시지와 같은 밀도로 쓴다

- **각 항목 1~2줄.** 결정 하나가 6줄을 넘으면 잘라낸다.
- 사실과 이유만. 평가·감상·수식어를 붙이지 않는다.
- 군더더기를 쓰지 않는다 — `~인 것 같습니다`, `~를 통해`, `~하도록 하였습니다`.
- 짧은 평서문 또는 명사형으로 끝낸다. 존대하지 않는다.

```
✅ 결정. MSW
   후보. json-server, 직접 fetch 래핑
   근거. 테스트에서 같은 handler 재사용 가능
   버린 이유. json-server는 별도 프로세스 필요
❌ 여러 가지 방법을 고민해본 결과 MSW를 사용하기로 결정하였습니다. 왜냐하면...
```

## 작업 원칙

- 결정의 **이유** 를 쓴다. 무엇을 했는지만 쓰면 기록의 값이 없다.
- 핵심 상태 로직을 대신하는 라이브러리를 썼다면 그 선택 이유를 반드시 남긴다.
- 나중에 뒤집힌 결정도 지우지 않는다. 뒤집힌 이유를 덧붙인다.
- 사용자가 말하지 않은 근거를 지어내지 않는다. 불분명하면 묻는다.
