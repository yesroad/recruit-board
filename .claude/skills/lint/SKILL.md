# Lint Skill

커밋 직전 타입·린트 오류를 정리한다.
**기계적으로 판정되는 오류만 다룬다.** 설계 판단이 필요한 문제는 `code-reviewer` 의 몫이다.

## Workflow

1. **패키지 매니저 판별.**
   lock 파일 기준 — `pnpm-lock.yaml` → pnpm, `yarn.lock` → yarn, `package-lock.json` → npm, `bun.lockb` → bun.
   판별할 수 없으면 사용자에게 묻는다. 임의로 실행하지 않는다.

2. **검사.**
   `<pm> lint` 와 `<pm> build` 를 실행한다. 해당 스크립트가 없으면 그 사실을 보고하고 종료.

3. **분류.**
   - 간단 — `prefer-const`, `no-console`, 사용처 없는 `no-unused-vars`, 추론이 명확한 반환 타입 누락.
   - 복잡 — `TS2322` `TS2345` `TS2339`. 타입 정의를 먼저 읽고 근본 원인을 파악한다. 표면만 맞추지 않는다.

4. **수정.**
   **하나씩 고치고 그 파일을 다시 검사한다.** 여러 오류를 한 번에 고치지 않는다 — 무엇이 무엇을 고쳤는지 알 수 없게 된다.
   우선순위는 타입 오류(컴파일 차단) → 린트 error → 린트 warning.

5. **전체 재검사 후 보고.**

## 금지

- **`any` · `@ts-ignore` · `eslint-disable` 로 우회하지 않는다.** 타입 오류는 대개 실제 결함의 신호다.
  우회 없이 못 고치는 오류는 **수정하지 말고** 사유와 함께 보고한다.
- 로직을 바꾸지 않는다. 오류를 없애려고 동작을 바꾸는 것은 이 스킬의 일이 아니다.
- 같은 오류가 2회 수정 후에도 남으면 멈추고 사용자에게 넘긴다. 반복 시도하지 않는다.

## 출력 형식

```
수정 완료. 파일 <목록> / 해결 N개 (간단 N · 복잡 N)
남은 오류. 타입 N · 린트 N
복잡 분류 수정. <파일:줄> — <무엇을 왜 고쳤나>
최종. 전체 통과 | 오류 N개 남음
```

복잡 분류를 고쳤으면 설계 판단이 섞인 것이므로 **`/prompt-log` 기록 대상** 이라고 알린다.
단순 린트 수정은 기록하지 않는다.
