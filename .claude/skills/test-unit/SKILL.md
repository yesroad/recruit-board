# Test Unit Skill

Vitest + Testing Library로 단위 테스트를 작성한다.
**눈으로 확인하기 어려운 것부터 덮는다** — 롤백, 경쟁 상태처럼 화면만 봐서는 통과처럼 보이는 로직이 우선이다.

## Workflow

1. **대상 확인.**
   테스트할 파일을 받는다. 없으면 무엇을 덮을지 묻는다.
   훅과 순수 함수를 우선한다. 렌더링만 하는 컴포넌트는 뒤로 미룬다.

2. **시나리오 도출.**
   Given-When-Then으로 케이스를 나열해 사용자에게 먼저 보인다. 성공 경로 1개 + 실패·경계 케이스 N개.
   **합의된 뒤에 코드를 쓴다.** 시나리오 없이 바로 작성하지 않는다.

3. **작성.**
   `<대상>.test.ts(x)` 를 대상 파일 옆에 둔다.
   MSW handler는 `src/mocks/handlers.ts` 의 것을 **재사용한다.** 테스트 전용 handler를 따로 만들지 않는다 —
   실제 mock과 어긋나면 테스트가 거짓말을 한다.
   특정 테스트에서만 실패·지연이 필요하면 `server.use()` 로 그 테스트에서만 덮어쓴다.

4. **실행.**
   lock 파일로 패키지 매니저를 판별해 `<pm> test` 로 돌린다 (`lint` 스킬과 동일한 규칙).
   **`test` 스크립트가 없으면 테스트를 작성하지 않고 종료한다** — Vitest 설치와 스크립트 추가가 먼저라고 안내한다.
   실패하면 원인을 분류한다 — 테스트가 틀렸는가, 코드가 틀렸는가.
   **2회 고쳐도 실패하면 멈추고 사용자에게 넘긴다.**

## 우선 대상

1. **낙관적 업데이트 롤백** — API 실패 시 이전 상태로 되돌아가는가
2. **경쟁 상태** — 늦게 도착한 응답이 최신 상태를 덮어쓰지 않는가
3. **검색·필터** — 대량 데이터에서 결과가 정확한가
4. **undo** — 직전 이동만 취소되는가

## 작업 원칙

- **구현이 아니라 동작을 검증한다.** 내부 상태 변수명·호출 횟수가 아니라 사용자가 관찰할 결과를 단언한다.
- **테스트를 통과시키려고 구현을 바꾸지 않는다.** 실패가 진짜 결함이면 그렇게 보고한다.
- `waitFor` 남용 대신 Testing Library의 `findBy*` 를 쓴다.
- 시간에 의존하는 로직은 `vi.useFakeTimers()` 로 고정한다.
- 커버리지 숫자를 목표로 삼지 않는다. 덮이지 않은 핵심 로직이 있는지만 본다.

## 입출력 프로토콜

- 입력. 대상 파일 + `src/mocks/handlers.ts`
- 출력. `<대상>.test.ts(x)` + 실행 결과 요약
- 형식.
  ```ts
  describe('useMove', () => {
    it('API 실패 시 카드가 원래 단계로 돌아온다', async () => {
      // Given  이동 전 상태 + 실패하는 handler
      // When   카드를 면접 단계로 이동
      // Then   카드가 서류검토로 복귀 + 실패 안내 노출
    })
  })
  ```
